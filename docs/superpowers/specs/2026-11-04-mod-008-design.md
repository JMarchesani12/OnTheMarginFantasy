# MOD-008 period and weekly-score identity

User authorized starting MOD-008 after MOD-006 rollout and MOD-011 verification.
Continue inline on audit, preserve existing week0/basketball/final-period dates,
scoring/tiebreak rules, complete response sets and existing job interfaces.

## Selected approach

Use Week(leagueId,weekNumber) and WeeklyTeamScore(leagueId,weekId,memberId) as the
natural identities. Serialize fresh ensure-weeks on the League row, recheck
existing rows inside that transaction, and persist the full precomputed boundary
plan atomically (including football week0). Existing complete/legacy collections
are returned unchanged: no automatic partial-history rebuild or deduplication.
Keep the fast existing-row read so season metadata is unnecessary on retries.
Read-only boundary planning precedes the write lock; concurrent calendar/settings
administration is not newly serialized by this task.

Score calculation remains existing orchestration. In the replacement transaction,
lock the scoped Week row before deleting/inserting; missing/replaced week fails
without altering existing scores. This serializes supported writers and ensures
fresh READ COMMITTED delete visibility after a competitor commits. It does not
make all upstream game/ownership facts one snapshot or fix job completion timing.

Alternative: uniqueness alone rejects a racing insert but does not make callers
converge; broad serializable retries add mutation/retry policy. Selected explicit
row locks plus constraints preserve existing valid responses and guard direct SQL.

## Schema and rollout

Separate aggregate-only RLS-fail-closed preflight reports duplicate week/score
keys and score-to-week/member league mismatches, never identifiers/private rows.
A bounded transactional migration rechecks under table locks, adds the two natural
keys and parent (leagueId,id) unique keys, then composite score FKs to enforce
same-league Week and LeagueMember with existing cascade semantics. Validate exact
constraint shape on replay. Preserve existing single-column FKs and frozen baseline.
No automatic cleanup, rekeying, score recomputation or schema rename.

Same-league references are already implicit in services and parent IDs; enforcing
them rules out cross-league rows rather than defining new scoring policy. Review
these composite FKs independently of natural keys in the migration/harness. Dirty
preflight blocks application and requires separately reviewed remediation.

## Verification and limits

Failing isolated tests for whole-plan rollback/retry and missing-week score guard;
real PostgreSQL start/ensure and score replacement races must observe lock waits,
leave one complete set, and restore prior state on statement/commit failure.
Baseline + kickoff + identity + new migration, upgrade/replay/dirty/mismatched
constraint checks and cross-league failures; rerun existing calendar/scoring
contracts and full isolated suite. Fresh independent review before rollout.
No hosted job/score generation, account/history remediation, main update/push or
application deployment. Backend deployment is separate from any SQL application.
