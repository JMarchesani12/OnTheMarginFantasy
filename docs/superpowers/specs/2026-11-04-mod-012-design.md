# MOD-012 admission and atomic league initialization

User confirmed numPlayers is the current member count and wants no hard league
limit. Existing automatic draft-round calculation remains for this correctness
task. A fair scaling system is a separate policy decision: eligible team supply,
equal roster sizes and conference limits must be considered. Do not interpret
maxPlayersToHaveMaxRounds as a maximum membership or invent last-slot rejection.

## Selected approach

Existing checked/job approvals already lock League before request/allocation;
retain and verify that serialization with current unique member/order keys. Make
the supplied-connection approval entry lock League itself before Request so it
has the same invariant, including trusted callers. Derive numPlayers from actual memberships after approval and initialize new leagues
at one creator; keep the existing round formula and response/authorization/replay
semantics. This corrects stale counters during approval, without a historical repair.

Pending-request creation takes League first, rechecks membership/existing PENDING
on that transaction, and returns the existing own request for competing calls.
No automatic APPROVED/CANCELLED transition or new capacity rule.

League + creator membership + complete calendar initialization share one caller-
owned transaction. Week initialization callable accepts conn= and uses that exact
connection, including league/season/settings/phase reads, locks and inserts. No
commit or second connection inside initialization. Supported calendar standalone
calls still own their transaction and keep existing-week fast read; supplied calls
leave commit/rollback to their caller. Failed insertion/planning/deferred commit
rolls everything back. Retrying a failed create leaves one usable league and no
duplicate weeks; lost-response idempotency/deduplicating distinct POSTs is not
invented. Existing persisted partial leagues are not silently rebuilt/deleted.

Alternative post-commit initialization with a durable pending lifecycle needs new
state/recovery/read visibility. Existing metadata-only calendar initialization
can run inside creation, so select atomic composition without new schema/state.
Standalone initialization retains the MOD-008 idempotent lock/recheck behavior;
calendar planning now uses the locked supplied connection rather than a detached
read plan. No provider/job/socket work is introduced into the transaction.

## Verification and boundaries

Failing creation/initializer rollback and supplied-connection tests; real PostgreSQL
initialization fault/deferred rollback/retry, concurrent same-request creation,
same/distinct approval order/count/round correctness, supplied entry and role/scope/
replay/rollback. Re-run previous native creation/admission/calendar suites and full
backend/frontend checks; independent review. Reuse installed MOD-008 constraints;
no migration, hard member cap, fairness rewrite, hosted league creation, jobs,
application deployment or merge/push. Keep work uncommitted on audit.
