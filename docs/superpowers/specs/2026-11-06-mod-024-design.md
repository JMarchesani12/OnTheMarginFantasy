# MOD-024 — Runtime recovery, readiness and safe operational reporting

## Intent and confirmed policy

Finish Priority 6's application reliability work after MOD-013/014/015/016/023.
An enabled disconnected/unhealthy draft listener makes a new `/ready` return503
until recovered. `/health` remains `{ok:true}`/200; intentional listener disablement
never blocks readiness. User explicitly selected this readiness policy. The remaining details below
are proposed implementation choices using the existing runtime. This closes application/synthetic verification scope;
hosted scheduler/roles/supervision and deployment remain separately unverified.

## Approaches

Recommended direction: keep the existing Flask/Socket.IO single-worker
runtime and PostgreSQL NOTIFY; add explicit recovery/control, readiness, safe logs
and job overlap handling. A managed queue/supervisor migration would change hosting,
credentials and deployment and is excluded. Merely logging listener death leaves
it dead and does not satisfy the recovery requirement.

## Listener connection and recovery

The injected application engine is the authoritative connection configuration.
Create a dedicated unpooled psycopg2 LISTEN connection using the engine dialect's
connection arguments, preserving SSL/connection options; never borrow a pooled
connection and leave LISTEN/autocommit/session state in the application pool.
Validate PostgreSQL/driver support before task startup. Add finite connection
setup timeout when absent. Never load .env or construct a configured engine inside
the listener definition/controller.

`DATABASE_URL` becomes an optional legacy consistency assertion, not an independent
connection source. If present, parse privately and compare normalized host/port,
database and role to the application engine. Malformed or different targets fail
before background startup with a fixed safe configuration error. Credentials/query
values are never printed. Different proxy/direct hostnames cannot be proven equal
from source: operators must remove the unused legacy variable after private target
review, rather than silently allowing a second target. Password differences are
irrelevant to target comparison because only engine credentials are used. No
hosted variable is changed by this task.

Controller states: starting, connected, retrying, stopped (plus disabled/not-started
runtime states). Successful connection and LISTEN are required before connected.
Connection/select/poll failures close resources and retry indefinitely with capped
exponential delay (1,2,4,8,16,30 seconds maximum, bounded jitter allowed). Backoff
resets only after established recovery. All waits are stop-aware. Idle polling
checks stop at least once per second; a periodic lightweight probe detects dead
connections, including silent idle failures. Network setup uses bounded timeout;
shutdown is cooperative, not a promise to preempt arbitrary driver/database I/O.

Malformed notifications are rejected safely without killing the listener. Snapshot/
delivery failures mark readiness degraded, log a safe category and retain bounded
coalesced league wakeups for retry; use a fixed maximum pending-league set, and if
it overflows close/reconnect and resynchronize current subscribed leagues rather
than accumulating unbounded payloads. Retried league snapshots use MOD-023's same
per-recipient authorization gate. No private payload is logged. On every successful
LISTEN/reconnect, refresh currently subscribed league rooms through that gate so
notifications missed during disconnect converge without a durable replay platform.
A subscription arriving during this work still gets its MOD-023 initial snapshot.
Failure for one league must not starve other league wakeups. Readiness recovers
only when the transport and pending delivery work are healthy. A retry/disconnect
cannot regress client state because MOD-023 uses serialized HTTP refresh signals.

Controller exposes idempotent start/stop and a safe status snapshot; store it in
app.extensions with its task handle. Repeated startup creates one task; stopping
closes owned resources and prevents further emits/retries. Preserve dev reloader
parent suppression. Wire explicit cleanup into development finally and a Gunicorn
worker-exit hook; no Flask request-teardown shutdown. No cross-worker broker.

## Readiness contract

Public `/ready` performs no database query. Return minimal fixed diagnostics with
`ok`, listener `enabled`/state and safe failure category;200 when disabled or
connected/healthy,503 while starting/not-started/retrying/degraded/stopped when
required. Construction-only create_app has no running listener and must not claim
listener readiness. No DSN, host, role, SQL, exception message, subject or token in
health responses. Keep existing `/health` and authentication/resource error shapes.
Readiness covers this web process's listener, not provider availability, cron last
success, another process, all database privileges or deployed supervision. Do not
advertise these additional guarantees.

## Operational logs and overlap policy

Use one small allowlisted structured logging helper for touched listener/timeout/
standard scheduled job adapters, with operation, generated run/connection ID,
fixed event/outcome/category, safe integer IDs/counts/date/duration. Never serialize
exception text/tracebacks, driver args, raw notification/snapshot/provider bodies,
DSNs, credentials or user/contact fields. Existing weekly/finalization report
return shapes and nonzero failure/block behavior stay compatible; structured logs
can accompany their bounded reports. Ingestion and schedule-refresh adapters must
stop printing raw provider/SQL exceptions, preserve per-unit continuation, and
signal partial failure to the CLI instead of a successful exit. Scope nested
logging in the called standard ingestion path so it cannot reintroduce raw errors;
broad bootstrap/checkpoint logging redesign and provider retry policy are excluded.

Standard one-shot cron adapters (weekly, finalization, live ingestion, future
schedule refresh) acquire a nonblocking PostgreSQL session advisory lock with a
stable namespaced key on a dedicated checked-out connection for the whole run.
A competing invocation of the same command skips with a structured already-running
outcome and exit0; it does no provider/domain work. These job gates do not replace
existing domain transaction/ownership locks. Different job types retain existing
transaction-level coordination and can run concurrently; no scoring/finalization
order or scheduler cadence change. Unlock/release on success/failure; invalidate
rather than return a connection to the pool if unlock fails. Process disconnect
releases the session lock; no stale lock rows/lease schema. Do not reconnect and
continue unlocked after gate connection loss: fail that invocation safely. Any
work already in an independent domain transaction retains its existing atomicity;
this is no exactly-once job execution claim. Timeout workers retain per-league
ownership/state-lock rechecks; multiple workers may poll, but one committed timeout
transition wins. No global worker lease or new scheduler infrastructure.

The timeout loop gets cooperative stop and safe correlated failure logs; retain
existing deadline/minimum-delay behavior. Standalone entry handles SIGTERM/SIGINT
through the stop control; injected tests do not install process signal handlers.
One-shot job termination relies on normal transaction rollback/process cleanup;
no new general process/signal framework.

## Operational inventory and Priority 6 closure

Document repository-observed commands: start.sh → one eventlet Gunicorn worker →
wsgi/runtime; dev reloader child; independent timeout worker; four one-shot jobs.
Document source behavior/cadence hints (live ingestion Central today and yesterday
before03:00, future refresh21days/daily recommendation, continuous timeout polling).
Do not invent deployed schedules or restart policies. No connected Render metadata
is available in the current tools; preserve the intentionally suspended service.
Record last known configured-role assessment as historical, not current Render
mapping. Provide operator smoke/recovery/shutdown and private DSN comparison steps
without running configured jobs or restarting services. Mark Priority6 application
work complete only after tests/review; retain hosted verification/rollout and
MOD-015 constraint follow-up as explicit limits, not unfinished app implementation.

## Verification

Failure-first tests: connection/LISTEN/select/poll/probe errors, reconnect/backoff,
stop during wait, idempotent registration and cleanup, pending snapshot failure
recovery, overflow bounds, reconnect resync and MOD-023 authorization. Credential-
shaped fixtures prove no raw values appear in logs/errors/readiness; configuration
parity tests include SSL/driver/port defaults and mismatch. Health tests use actual
Flask routes with injected state and confirm unchanged `/health`.

Actual PostgreSQL owned marked loopback test connections prove LISTEN disconnect/
reconnect/current authorized snapshot refresh, dedicated connection cleanup, cron
lock contention and release on exception/disconnect. No configured DSN/app/runtime,
real listener/worker process, provider call or hosted job is run. Controlled calls
exercise the production controller in tests. Full backend/frontend/build and prior
native notification/ownership contracts rerun; fresh independent final review and
source-hashed evidence. No migration/dependency/deploy/commit/push.

## Builder discretion

File boundaries, task-loop injection and fake-clock/socket design, exact allowlisted
log keys, status synchronization and pending-set implementation are implementation
choices. Use modest fixed constants and tests, preserve import isolation and
existing public draft events/HTTP contracts. If any requirement needs new external
infrastructure or a deployed configuration decision, leave that evidence gap open.
