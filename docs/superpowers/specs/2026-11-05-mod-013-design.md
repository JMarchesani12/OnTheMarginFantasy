# MOD-013 — Retry-safe weekly closure and pending application

## Intent and agreed policy

Priority 6 begins with MOD-013 only. User confirmed pending trades/free-agent
changes become eligible once their assigned week's preceding week successfully
closes, including retries with no newly ended weeks. Preserve scoring math,
trade deadlines, veto rules, conference checks and existing per-command validation.
No scheduler rollout, configured jobs/data mutations or new infrastructure.

## Approaches and recommendation

Recommended: compose existing scoring and transaction services with supplied
connections. Commit each weekly score replacement, completion marker and next-week
lock together; use existing Week.scoringComplete and Transaction.status as durable
progress. Pending application remains individually atomic and retryable.

Alternative: durable queue/run ledger with claims and recovery states. Adds schema
and operational machinery without a demonstrated need for this bounded workflow.
A single transaction for an entire multi-league run would couple failures and hold
locks too long. Neither alternative is recommended.

## Closure and ordering

A weekly orchestration service, called by the startup-isolated cron adapter, owns
ordering. Discover leagues with ended incomplete weeks OR pending work, including
runs with no scoring candidates. Recheck candidates under the shared per-league
ownership advisory mutex, before Week/Transaction row locks. Serialize overlapping
weekly workers and ownership writers using the existing v1 mutex protocol.

For each league, process periods chronologically. Before scoring an ended target
week, apply its eligible pending changes; never score it while eligible changes
remain unapplied or have failed. Close its predecessor first if needed. Apply
newly eligible changes after closure even when their target has not yet ended.
Do not process future targets early simply because a different league/week closed.
Use actual predecessor periods in the same league, including football week zero;
missing calendar predecessors must not accidentally grant eligibility.

Score replacement + marking that exact week complete + locking its next existing
period share one transaction. Recheck ended/incomplete state under lock; another
worker finding completion skips replacement. Rollback on calculation/write/commit
failure leaves the period retryable with prior scores and flags intact. Calculation
must run after preceding ownership work and while the league mutex is held;
thread supplied connections through the necessary scoring/schedule reads rather
than opening competing transactions. Keep existing standalone scoring contracts.

## Pending application and failure recovery

Eligibility requires same-league target and predecessor, predecessor successfully
complete, and target not scored. Recheck eligibility under the league mutex and
transaction row lock in the application transaction. Preserve current checked vs
trusted entry points; the weekly caller cannot bypass existing apply guards.
Recheck status: already completed by a competing worker is a deliberate skip,
not a job failure. Pending changes for scored targets are reported and retained;
do not rewrite historical rosters or silently retarget them.

Apply deterministically by target period then transaction ID, each command with
its own commit. A failed command keeps its PENDING_APPLY status and ownership
unchanged; stop later application/closure in that league for that run to avoid
ignoring dependencies. Other leagues continue. Earlier committed commands are
not undone or repeated on retry. No automatic cancellation or infinite in-run
retry. Log/report scoped IDs and safe categories without payloads/credentials.

First calendar period has no predecessor: the confirmed rule does not establish
eligibility there. Leave such pending rows untouched and explicitly report them
for policy/operator review; do not invent initial-period application. This is a
conservative boundary, not an automatic history repair.
