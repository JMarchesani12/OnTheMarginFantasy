# MOD-006 linked-profile uniqueness

Continue the user-authorized first Priority 5 task inline on audit. MOD-002 principal isolation and MOD-005 baseline dependencies are satisfied in their documented scopes. Hosted preflight/DDL is not authorized by this local implementation.

Preserve nullable legacy/job UUIDs and the existing unique-email policy. Enforce at most one User for each non-null auth subject with a named, nondeferrable User_uuid_key unique constraint. Interactive creation still requires verified subject/email; null legacy rows cannot authenticate through subject lookup. No automatic account linking, deletion, merging, email updates or NOT NULL conversion.

Alternatives: NOT NULL would break supported unlinked job rows and require account remediation; application-only locking would not protect direct database writers. Selected: database uniqueness for linked subjects, preserving the existing null/email policy. This is the maintainer-authorized recommended implementation with compatibility decisions made by the implementer.

Aggregate-only read-only preflight reports total/unlinked counts and duplicate subject-group/affected-row counts without identifiers or private values. The migration takes a bounded table lock and repeats duplicate checks inside its transaction before adding uniqueness; duplicate legacy state aborts with a generic remediation message. Replay validates the named constraint's actual shape. Freeze the original baseline; add an explicit later migration and update the current intended schema snapshot/run order.

Interactive creation retains the existing precheck/409 behavior. If a PostgreSQL unique violation occurs during a concurrent insert/commit, rollback first, then make one fresh subject lookup: exactly one profile means ProfileAlreadyExists/409; multiple means existing ambiguity denial; absent means safe existing creation rejection/400. Other SQLSTATE failures preserve existing safe handling. Do not return or overwrite another profile, or retry mutations. Trusted job failures remain generic; nullable UUID support remains.

Verify duplicate preflight/migration refusal and atomicity, replay/shape drift, two concurrent same-subject first logins (same and different email), unique email conflicts across subjects, multiple null legacy profiles, FK failures and rollback on real marked disposable PostgreSQL. Keep backend authorization/startup and browser contracts green. No hosted claims or migrations, dependency installs, merge/push/deployment or real jobs.


Preflight and migration explicitly set row_security=off to fail when the caller
would see a filtered table, without bypassing RLS. Replay also validates the
backing index is valid/ready and uses null-distinct semantics. Both failure
conditions have native regressions. Current intended snapshot includes the
constraint; hosted installation/preflight remain unperformed.
