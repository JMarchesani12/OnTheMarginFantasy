# MOD-014 — Atomic sport-season finalization

## Intent and approved completion policy

User chose atomic finalization per sport-season: require all its weeks closed,
pending changes resolved and every league's standings validated before committing
league completion updates and SportSeason.seasonFinalized together. Failures leave
that season retryable; unrelated seasons continue. Existing Flask decoupling is
already complete and must not be reimplemented.

## Approaches

Selected: one transaction per sport-season, composing the existing trusted standings
service with a supplied connection. Existing seasonFinalized is the success marker;
no new progress table or migration. Per-league partial commits were considered but
would need a distinct progress marker: lifecycle code already sets League.status
Completed by date, so that status cannot establish successful finalization.
A single global transaction would unnecessarily couple independent seasons.

## Eligibility and validation

Select ended unfinalized seasons as hints. Since seasonEnd is an inclusive date,
require seasonEnd < current UTC date; the season-end day alone cannot authorize
finalization. Recheck dates and flag after locking the season. Every selected
league must have a nonempty calendar, all periods ended and scoringComplete=true,
and no PENDING_APPLY transactions. A missing/null date or incomplete/invalid period
blocks that season. Preserve MOD-013 first/scored-target pending boundaries: do not
apply, cancel or retarget commands here. PROPOSED trades are not PENDING_APPLY and
are not automatically resolved by this task.

Cover all existing leagues matching exact sport + seasonYear, including those
already marked Completed by lifecycle. Do not skip validation based on league
status. No matching leagues is reported as blocked instead of finalizing an empty
scope. Pre-Draft/empty/incomplete leagues can block; do not invent exemptions.

Call trusted standings service using the same transaction for all underlying reads
and rule/bonus/tiebreak helpers. Validate ordinary success dictionaries, matching
leagueId, members matching current league membership exactly without duplicates,
and finite numeric weeklyPoints/bonusPoints/totalPoints. Empty membership, error
payloads/HTTP tuples, missing/foreign members and nonfinite totals are failures.
Do not change scoring formulas, season tiebreakers, bonus rules or HTTP projections.
Standings/bonuses remain computed reads; no BonusPointEvent or persisted snapshot.

## Transactions and concurrency

Lock SportSeason first; then acquire existing v1 ownership advisory mutexes for all
candidate league IDs in ascending order, before League/Week/Transaction row locks.
Re-read and lock each league, period and relevant pending state on the supplied
connection. Recheck league sport/year after locking, and compare scope again before
setting the flag; abort on a detected scope change rather than mark an unvalidated
league. Update only explicitly validated league IDs, not an unbounded matching
UPDATE. All validation and league/season updates share the one transaction.

Competing finalizers recheck the flag and deliberately skip after the winner commits.
Weekly closure/application and trade actions use the same ownership mutex and
serialize with finalization. Calculation/write/deferred-commit failure rolls back
all this transaction's league/status/flag changes; pre-existing lifecycle Completed
statuses are not undone. Failed season is isolated and retry recomputes validation.

This marker records successful validation of the scoped league set, not an immutable
season seal. It does not prevent later league creation, roster edits, provider or
rule changes. Detected concurrent scope changes cause refusal, but preventing every
future/predicate-phantom insertion would require changing all administration writers
or stronger schema/state policy; that is outside MOD-014. Historical immutability
and explicit maintenance recovery remain MOD-015/016. No claim of frozen standings.

## Adapter and operations

Keep build_scoring(engine) transport-independent and configured_engine loading lazy.
Cron delegates to a focused finalization service/repository and returns/prints a safe
report of finalized/skipped/blocked/failed season IDs and scoped reasons/categories.
Nonzero CLI exit if failures or blocks remain, without exception SQL/payload logging.
No configured job run, scheduler modification, app/provider startup or deployment.
Work in the current audit checkout and leave changes uncommitted.

## Verification

Failure-first isolated tests cover actual orchestration outside Flask: malformed
success, empty/partial scope, incomplete/future weeks, pending commands, date boundary,
pre-existing Completed status, exact sport/year scope, all-or-nothing update and
failure isolation/retry. Native owned marked loopback PostgreSQL uses frozen schema
plus current migrations and real standings/bonus/tiebreak reads, strict supplied
connection guards, statement/deferred-commit rollback, overlapping finalizers and
weekly/transaction lock waits, plus prior scoring/weekly regressions. Verify HTTP
season projection unchanged, full backend/frontend/build/diff checks and source-
hashed evidence. Independent final review. No new SQL rollout is expected.
