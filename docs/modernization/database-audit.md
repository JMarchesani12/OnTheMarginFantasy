Primary keys exist on every distinct table; most use bigint identity, DraftState is keyed by league and DraftTurn by league/pick. ## DB-01 — Migration provenance is incomplete (D/M)

Evidence: `db/tables.sql` repeats DraftPick and its indexes, creates ConferenceMembership before its referenced tables, and uses `gin_trgm_ops` without declaring the required extension. It references Supabase-owned auth.users. It is a descriptive snapshot, not a safe ordered blank-database migration. The explicit `(leagueId, overallPickNumber)` DraftPick index duplicates the unique constraint's key; actual deployed redundancy/usage is unknown.

Only `20260803_create_sport_season_subdivision.sql` and `20260803_fix_sport_season_start_column.sql` exist. The first creates a constrained table inside BEGIN/COMMIT; the second conditionally renames `esasonStart` if the correct name is absent. It does not resolve both-column or neither-column states. Both share a date; no runner/order/version ledger is checked in. Database and season setup READMEs reference absent `20261023_basketball_tournament_rules.sql`, while snapshot already has SeasonPhase.rules. The README says it is based on live schema, but provides no dated export/provenance; that is not current live metadata evidence.

Benefit of repair: reproducible setup and safer future changes. Backlog MOD-005 separates migration reconciliation from data/constraint changes. Do not invent the missing migration's contents or apply either existing migration during an audit.

## Integrity and transaction boundaries

- **DB-04 (D):** `ScoringModel._delete_existing_weekly_scores:116–127` commits deletion separately from replacement insertion at `compute_weekly_scores:265–289` (backend D06). A replacement failure can leave no scores. Missing score uniqueness additionally allows duplicate computations under concurrency (G). MOD-007 handles atomic replacement; MOD-008 separately establishes score/week natural keys and concurrency behavior.
- **DB-05 (G/I):** Snapshot lacks ownership overlap and tenant-consistency guards described above. Live draft/timeout serialize via DraftState FOR UPDATE and unique DraftPick keys, but this does not establish serialization for free agency/trade/manual combinations. `TransactionModel.apply_trade:690–798` locks the transaction but lacks locked type/status checks (backend D07); that is a source defect independent of whether overlapping rows already exist. MOD-009 fixes application transition/replay behavior; MOD-010 investigates cross-command concurrency and adds justified DB guards only after preflight.
- **DB-06 (D/G):** Join deny/cancel compare lowercase pending against uppercase inserted/checked PENDING; denial also has trailing comma before WHERE (`LeagueModel:845–910`, backend D04). Partial unique pending protects duplicates but does not resolve check/insert race responses. Approval computes order before later league lock (backend S02). MOD-011 repairs status/SQL; MOD-012 independently verifies admission/capacity/order serialization.
- **DB-07 (I):** `ensure_weeks_for_league` checks existing then separately inserts week0 and later weeks (`scheduleModel:277–367`); League creation commits before ensuring weeks. No unique league/weekNumber is shown. Weekly job scores, then marks/locks, then globally applies pending; no-weeks early return skips application, failed leagues remain eligible for global pending selection. Final job calls jsonify adapter without app context and checks no outcome before completion updates (backend D08/S02). MOD-008/013/014 cover distinct boundaries; timing is product Q3, not settled through refactoring.
- **DB-08 (G/I):** ConferenceMembership allows current and season-specific rows simultaneously. `ScheduleModel.search_teams_for_league` joins `(seasonYear IS NULL OR seasonYear = :seasonYear)` with no fallback precedence: a team can yield multiple rows if both exist. Several roster/ownership joins need the same review. This is a query cardinality risk allowed by the schema, not evidence of existing duplicates. MOD-015 establishes explicit seasonal precedence and sport/season consistency, preserving independent-team handling.
- **DB-09 (I):** Rebuild/rescore updates/deletes weeks and scores but does not establish migration of ownership interval week numbers or transaction period meanings (`api/scripts/rebuild_weeks_and_rescore.py`, behavior Q6). Phase rules and current tiers affect history. MOD-016 requires a historical-integrity policy, dry-run impact summary and synthetic replay/recovery before expanding maintenance use. No automatic snapshot or data conversion is justified yet.

## Retrieval, repetition and pagination

**DB-10 (I):** No latency, pg_stat_statements, query-count trace, row-count/response-size measurement or execution plan was supplied. Thus no finding is a measured slowdown.

- Search leagues caps limit 50 and clamps offset but has no maximum offset; ordering similarity/name lacks id tie-breaker. Equal names/scores can make page order unstable. MOD-018 first records cardinality/plan and defines deterministic ordering; cursor changes require explicit API/client agreement, not an automatic rewrite.
- Team search loads all sport candidates, joins ownership/conferences, then normalizes/ranks and slices to <=50 in Python (`scheduleModel:1515–1604`). The response limit does not limit DB retrieval. Pushdown must preserve abbreviation/prefix ranking and seasonal precedence; MOD-018 requires fixture equivalence and measurements first.
- Own leagues, open/pending transactions, member rosters, team-season schedules and draft snapshots are unpaginated. Some are naturally season/league-sized; that is not proof of dangerous size. Do not page a complete roster or draft snapshot and silently break callers. Record counts/bytes; cap user-supplied pointsAwarded week arrays/trade arrays with explicit validation (MOD-019), then paginate only collections with demonstrated need (MOD-018).
- League detail/member scoring loops load games per member, rules repeatedly, and additional tie-break queries. Home/league context/profile independently repeat resources; `get_league/get_leagues_for_user` run five global status UPDATEs on reads (backend S01). These are source-visible work amplification and a surprising write-on-read path, not measured contention. MOD-020 measures and removes global writes from ordinary reads with equivalent lifecycle timing; MOD-021 measures member/weekly queries before batching; MOD-026/029 address browser ownership.
- Cron ingestion loops active leagues and re-fetches/upserts global same-season games; event-level team/phase lookups and individual transactions amplify work (backend S04). Existing sport-season dedup/upsert is useful. MOD-022 measures provider/DB counts and consolidates per-season ingestion without changing classifications.

## Potentially obsolete structures and drift

`BonusPointEvent` is described in db/README and endpoint comments but absent from snapshot; actual season standings compute bonuses in ScoringModel. This is a documentation/provenance discrepancy, not justification to create/drop a table. Preserve computed output; confirm any deployed table and external writers first (MOD-005/035). No other table is established unused: inventory and SQL consumers cover identity, catalog, seasons, draft, ownership, transactions and scoring. Deprecated sport CLIs, unregistered lock helper, alternative NCAA/socket auth and magic-link helper require external usage evidence before removal. Duplicate index/DDL and misleading index names are not permission to delete deployed objects.

No deployed metadata was available, so **schema drift cannot be verified**. Future read-only metadata collection (MOD-004/005) should use a read-only transaction and timeouts, target the known project, and avoid application rows: columns/defaults/identity, PK/FK/CHECK/unique/index definitions, RLS flags/policies/grants/default grants, roles/owners/BYPASSRLS, views/functions/triggers/EXECUTE/search_path, extensions/publications, migration ledger if present and scheduler metadata with credentials/command secrets redacted. Compare normalized definitions to a dated export and repository history. Use aggregate-only violation counts for preflights; do not export emails, UUIDs, transaction JSON or raw query parameters.

For query work, begin with schema and parameterized EXPLAIN without ANALYZE. Costs/estimates are not runtime measurements. On an isolated representative fixture, collect execution time, buffers, rows returned/scanned, query count and payload size using EXPLAIN (ANALYZE, BUFFERS) for read-only SELECTs and request traces. Never EXPLAIN ANALYZE a mutation, arbitrary function or job against production. Inspect plans/traces for literal/private values before saving. No such evidence was generated here.
