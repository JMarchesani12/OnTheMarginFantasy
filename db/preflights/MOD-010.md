# MOD-010 ownership integrity and concurrency

Ownership uses half-open `[acquiredWeek,droppedWeek)` intervals: acquisition is
inclusive, drop is exclusive, NULL end is unbounded. Week0 remains valid. Empty
same-week intervals (`start=end`) carry history without owning any period and
remain valid. Adjacent transfers and existing future intervals remain valid;
conflicting open-ended writes fail rather than truncating/remapping future rows.

## Application boundary

All first-party live/manual/timeout draft writers, pending free-agent submission/
application and trade application acquire one transaction advisory mutex per
league before DraftState or Transaction row locks. `utils/ownership.py` defines
the stable v1 SHA-256-to-signed64 key. Keep that protocol unchanged across mixed
versions; unrelated hash collisions only add serialization, never grant access.
Independent leagues do not share a mutex. Private repository/insert helpers are
not independent commands: callers must enter through the owning command, and
supply its connection/mutex. Direct SQL writers rely on database constraints.

Free-agent routing, swap counts, member/pending checks and writes now use the
same locked transaction. Existing direct helper calls remain supported with an
optional supplied connection; subclass overrides used inside mutable commands
must accept/pass that connection. Applying queued free-agent work rechecks drops,
actual add availability and post-drop conference caps before completion. Invalid
work stays pending and rollback restores all slots. No mutation retry is added.
Trade type/status/replay and deadline checks remain; the initial transaction
league hint is compared with the subsequently locked row before ownership work.

Pending reservations retain their existing requested-week behavior; this does
not guarantee every independently queued future operation will still be valid
when applied. The authoritative application checks reject stale/conflicting work.
No new cross-week queue priority, scheduler timing, automatic cancellation or veto
policy is chosen. MOD-013 owns dependency/retry handling; membership/calendar
administration and season-specific conference semantics remain separate concerns.

## Database objects

- `LeagueTeamSlot_interval_check`: start>=0 and NULL end or end>=start.
- `LeagueTeamSlot_same_league_member_fkey`: (leagueId,memberId) references
  LeagueMember(leagueId,id), preserving ON DELETE CASCADE. Requires MOD-008 key.
- `LeagueTeamSlot_no_overlap`: nondeferrable GiST exclusion on league/team equality
  and `int8range(start::bigint,end::bigint,'[)')` overlap.

The exclusion protects direct SQL and future intersections even if a caller has
an old point-in-time availability check. Empty ranges never overlap. PostgreSQL's
platform-supplied `btree_gist` extension supplies scalar equality GiST classes.
The migration enables it in public only if absent; an existing installation is
preserved in its current schema. No package download/service installation occurs.
The index adds write/storage work; no performance improvement is claimed.

The member FK enforces tenant consistency. Team/league sport mismatches are
reported by preflight; a new cross-table sport constraint is not introduced here.
Existing foreign keys and all historical row IDs/data are preserved.

## Other environments, remediation and recovery

1. Authorize/confirm target and run [aggregate preflight](20261104_ownership_integrity.sql).
   Counts only: slots, negative/reversed/empty intervals, wrong member league/sport,
   overlapping pairs and adjacent transfers. Empty/adjacent counts are informational;
   other non-total counts must be zero. RLS-filtered readers fail closed via
   row_security=off; use a role authorized for complete relevant tables.
2. Stop on dirty counts. Review intended owners/effective weeks and dependent
   history separately with authorized private access. Do not delete duplicate
   rows, shift acquisition weeks, truncate future intervals or infer a winner from
   row IDs. Approved remediation/reversibility is a separate task.
3. Confirm extension availability and MOD-008 parent key, then run the complete
   [migration](../../api/migrations/20261104_ownership_integrity.sql) transaction.
   It enables the standard extension, locks the slot table, rechecks bad history,
   validates null policy and existing named definitions, and adds only the three
   guards. Lock timeout5s/statement timeout60s bound contention; stop on error.
   Extension creation is transactional and rolls back with a failed fresh migration.
4. Verify check expression, ordered FK keys/target/actions, exclusion expression/
   operators/access method/index readiness/nondeferrability, and aggregate counts.
   Deploy all reviewed web/job writers through the normal application process.
   Constraints protect intervals immediately; pending reservation serialization
   and application cap checks require all writers to run the updated code.

Fresh initialization order: frozen October29 baseline, October30 kickoff,
November4 User identity, week/score identity, then ownership integrity migration.
Frozen baseline files/checksums are unchanged. Current db/tables.sql is a target
snapshot requiring the extension and migration sequence, not a standalone setup.

Operational rollback requires separate review: dropping the introduced exclusion,
check or member FK preserves rows but removes its safety guarantee. Keep original
FKs/PKs and v1 application mutex intact. Leave btree_gist installed; do not DROP
EXTENSION CASCADE because other objects may depend on it. Recheck history before
reinstalling constraints. No rollback performs ownership cleanup/recomputation.
