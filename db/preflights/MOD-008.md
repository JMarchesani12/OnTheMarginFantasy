# MOD-008 week/score identity rollout

The application serializes supported fresh week initialization on League and
writes the whole plan, including football week0, in one transaction. Concurrent
ensure calls recheck after the lock and return the same canonical rows. Existing
rows are returned without rebuilding season history. Calculations/UTC boundaries,
basketball opening/final-period rules and response projections are preserved.
Legacy partial plans are not silently repaired.

Score calculation retains its existing reads and ranking. Replacement locks the
scoped Week row before delete/insert; a missing/replaced period fails before
mutation. A waiting replacement sees and replaces the committed prior set.
This is not a transactionally consistent snapshot of games/ownership/membership,
nor a job completion/retry redesign (MOD-013/015 remain separate).

## Keys and same-league references

| Object | Identity or relationship |
| --- | --- |
| Week_league_week_number_key | UNIQUE(leagueId,weekNumber) |
| Week_league_id_key | UNIQUE(leagueId,id), composite FK target |
| LeagueMember_league_id_key | UNIQUE(leagueId,id), composite FK target |
| WeeklyTeamScore_identity_key | UNIQUE(leagueId,weekId,memberId) |
| WeeklyTeamScore_same_league_week_fkey | (leagueId,weekId) → Week(leagueId,id), delete cascade |
| WeeklyTeamScore_same_league_member_fkey | (leagueId,memberId) → LeagueMember(leagueId,id), delete cascade |

Natural identities prevent duplication across every writer. Composite FKs are
reviewed separately to enforce the already intended same-league relationship;
they retain cascade semantics and existing single-column FKs. The two parent
unique indexes add storage/write cost to support these explicit references.
No scoring/history rows are merged, updated, removed or recomputed by migration.

## Other environments and dirty data

1. Authorize/confirm the target and run [aggregate preflight](20261104_week_score_identity.sql).
   It reports totals, duplicate groups/rows, null identity keys and missing or
   cross-league week/member references. No identifiers, player names or history
   rows are exported. row_security=off fails for filtered readers rather than
   implying readiness; use a role authorized for the complete tables.
2. Stop if any non-total count is nonzero. Review history/remediation separately:
   duplicated weeks may be referenced by scores/transactions/ownership, and
   duplicated scores cannot be summed or selected arbitrarily. Choose approved
   authoritative mappings with a reversible audit, not automatic ID-based cleanup.
   Preflight does not establish whether a legacy calendar plan is complete;
   inspect expected boundaries through a separately approved history process.
3. With clean counts and operational authorization, run the complete
   [migration](../../api/migrations/20261104_week_score_identity.sql) as one transaction,
   stopping on any error. It locks Week, LeagueMember and WeeklyTeamScore in that
   order, rechecks dirty state, verifies NOT NULL policy and validates exact named
   constraint/index/FK semantics on replay. Lock timeout5s and statement timeout60s
   bound busy-table waits; investigate/retry in a suitable window instead of
   disabling guards. DDL can briefly block normal reads/writes; no runtime job
   or migration auto-start is introduced.
4. Verify all six catalog definitions, readiness/validation/nondeferrability,
   null-distinct unique semantics and FK target/order/delete/update/match policy.
   Rerun aggregate counts. Deploy application locking changes through the normal
   application process: database constraints alone reject bad writes, but cannot
   provide atomic multi-transaction initialization in an old deployed backend.

Fresh initialization: frozen October29 baseline, October30 kickoff migration,
November4 User identity migration, then November4 week/score identity migration.
Keep frozen checksums unchanged; its runner checks its original historical
catalog, not this upgraded target. Current db/tables.sql records the target.

An operational rollback is a separate reviewed action. Drop introduced child
composite FKs before their parent unique keys; removing natural keys reopens
races for direct/old writers. Leave original FK/PK constraints intact, preserve
rows, coordinate writes and rerun readiness checks before reinstalling. Application
locks remain compatible with the prior schema, but direct-writer guarantees then
no longer hold. No cleanup/rebuild SQL is part of this rollback guidance.
