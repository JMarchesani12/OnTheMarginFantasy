# MOD-015 seasonal consistency

Run `20261105_seasonal_consistency.sql` read-only on an explicitly authorized target.
This stage ran it only on owned synthetic PostgreSQL. It returns counts, no private
rows. Missing mappings are configuration defects; do not synthesize independent
buckets or guess conference assignments. Seasonal data overrides current fallback;
invalid exact-season data must be investigated, not masked by defaults.

## Delivered guarantees

Repositories use a shared effective-membership relation with sport agreement.
Draft/transaction commands validate affected and retained roster mappings on their
transaction before ownership writes. Game ingestion validates/locks SportSeason,
optional SeasonPhase and known SportTeam reference rows with FOR SHARE on its supplied
connection before upsert. Nullable external participants and nullable phase are valid.
These are application boundaries, not constraints on arbitrary SQL or future updates.

## Constraint proposal and rollout dependency

After reviewing counts and the exact deployed catalog, prepare composite unique keys
SportTeam(id,sportId), SportConference(id,sportId), SportSeason(id,sportId), and
SeasonPhase(id,sportSeasonId). Proposed composite FKs:

- ConferenceMembership(sportTeamId,sportId) → SportTeam(id,sportId).
- ConferenceMembership(sportConferenceId,sportId) → SportConference(id,sportId).
- GameResult(sportSeasonId,sport) → SportSeason(id,sportId).
- GameResult(seasonPhaseId,sportSeasonId) → SeasonPhase(id,sportSeasonId), MATCH SIMPLE
  to preserve nullable phase; team references additionally require sport agreement.

Membership sportId is nullable in the observed baseline. Composite FKs alone let
NULL bypass validation: review those rows and explicitly approve a NOT NULL policy
before claiming full protection. Parent sport changes, deletion actions, existing
index shapes/privileges and tournament-season/conference links also need catalog
and dirty-data review. A basic FK cannot ensure that every team has an effective
mapping for every season; that coverage remains preflight/application validation.

No migration is shipped/applied by MOD-015: absent target metadata/dirty-row decisions,
adding parent keys and NOT NULL semantics would overclaim safe rollout. A future
migration must prove clean upgrade/replay, dirty atomic refusal and parent/direct
write cases on synthetic PostgreSQL before authorized target rollout. Existing
partial membership unique indexes and frozen baseline are retained. No automatic
backfill, historical rewrites or configured metadata/data access occurred.
